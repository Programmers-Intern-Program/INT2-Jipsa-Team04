# 재인제스트·부분 실패·보상 처리 정책

> **문서 상태:** Stable · 데이터 정합성 핵심 정책  
> **주 독자:** 색인 서비스 개발자, DB·Qdrant 운영자, 장애 대응 담당자  
> **최종 검토:** 2026-07-28  
> **핵심 보장:** 신규 실패가 이전 정상 검색 상태를 제거하지 않아야 함


## 1. 목적

인제스트는 Local RAG DB와 Qdrant라는 서로 다른 저장소를 함께 변경합니다.
이 문서는 재인제스트, 동시 요청, 부분 실패와 보상 처리 시 이전 정상 검색 상태를
보존하는 규칙을 정의합니다.

## 2. 인제스트 단계

```text
1. Backend에서 최신 manifest 조회
2. Presigned GET URL 다운로드와 원본 검증
3. 형식별 파싱
4. 이미지 추출·렌더링·OCR
5. 구조 보존 청킹
6. CUDA TEI 임베딩
7. File_IDX advisory lock 획득
8. Local RAG DB 색인 준비
9. Qdrant 비활성 staging point 업서트
10. 신규 point 활성화
11. 이전 정상 point 비활성화
12. Local RAG DB SUCCESS·INDEXED 확정
13. 최신 활성 청크 스냅샷 조회
14. Backend ingest-complete 성공 콜백
```

검색 불가 구간을 만들지 않기 위해 신규 point를 먼저 활성화한 뒤 이전 point를
비활성화합니다. 짧은 중복 노출 가능성보다 정상 검색이 완전히 사라지는 위험을 우선
방지합니다.

## 3. 색인 정체성

다음 값이 같으면 동일 정상 색인을 멱등 재사용할 수 있습니다.

- 파일 SHA-256
- Parser Version
- Embedding Model
- Index Version

동일 정체성에서는 결정적 Chunk ID를 재사용합니다.
파서, 임베딩 모델, 청킹 또는 색인 계약이 달라지면 신규 RAG 문서와 point를 생성합니다.

## 4. 재인제스트

### 동일 정체성

- 기존 정상 문서와 청크를 재사용합니다.
- 기존 활성 point를 삭제하지 않습니다.
- 이번 실행 이력은 독립적으로 기록합니다.
- 재사용 실행이 실패해도 기존 정상 문서 상태는 `INDEXED`로 유지합니다.
- 실패한 실행만 `FAILED`로 기록합니다.

### 변경된 정체성

- 신규 문서와 청크를 준비합니다.
- 신규 Qdrant point를 `is_active=false`로 staging합니다.
- 전체 업서트가 성공한 뒤 신규 point를 활성화합니다.
- 이전 정상 point를 비활성화합니다.
- Local RAG 성공 확정 후 이전 문서를 soft delete합니다.

신규 흐름이 끝까지 성공하기 전에는 이전 정상 색인을 제거하지 않습니다.

## 5. 동시 인제스트

같은 `File_IDX`의 색인 임계 구역은 MySQL advisory lock으로 직렬화합니다.

보장 사항:

- 두 요청이 같은 문서와 결정적 Chunk ID를 동시에 변경하지 않습니다.
- 뒤따르는 동일 요청은 최신 정상 상태를 재조회해 멱등 수렴합니다.
- 성공 콜백용 최신 활성 스냅샷 조회도 같은 `File_IDX` lock 안에서 수행합니다.
- 이전 요청의 콜백이 늦게 도착해도 콜백 시점의 최신 SUCCESS 스냅샷을 사용합니다.

## 6. 실행 소유권 상실

오래된 실행이 더 최신 실행에 의해 소유권을 잃으면 다음 규칙을 적용합니다.

- 오래된 실행은 최신 실행이 만든 Qdrant point를 삭제하지 않습니다.
- 이전 문서를 임의로 재활성화하지 않습니다.
- 오래된 실행 이력만 실패로 정리합니다.
- Qdrant 보상 작업을 건너뛴 사실을 안전한 식별자와 오류 종류만 로그로 남깁니다.

## 7. 보상 처리 매트릭스

| 실패 위치 | 이전 정상 색인 | 신규 point | Local 실행 상태 |
|---|---|---|---|
| manifest 조회 | 변경 없음 | 생성 전 | 호출 오류 반환 |
| 다운로드·형식 검증 | 변경 없음 | 생성 전 | 실패 콜백 시도 |
| 파싱·청킹·임베딩 | 변경 없음 | 생성 전 | 실패 콜백 시도 |
| 신규 Qdrant 업서트 | 유지 | 신규 staging만 삭제 | FAILED |
| 신규 point 활성화 | 재활성화·유지 | 비활성화 후 삭제 | FAILED |
| 이전 point 비활성화 | 이전 point 재활성화 | 신규 point 삭제 | FAILED |
| Local SUCCESS 확정 | 이전 point 재활성화 | 신규 point 삭제 | FAILED |
| 기존 정상 색인 재사용 중 실패 | 그대로 유지 | 기존 point 삭제 금지 | 이번 RUN만 FAILED |
| 실행 소유권 상실 | 최신 상태 유지 | 보상 금지 | 오래된 RUN만 FAILED |
| 성공 콜백 네트워크 오류 | Local 성공 상태 유지 | 활성 상태 유지 | 원래 콜백 오류 반환 |

보상 처리 자체가 실패해도 최초 오류를 덮어쓰지 않습니다. 보상 오류는 별도 안전 로그로
기록하며 운영자가 Qdrant와 Local RAG DB 상태를 확인해야 합니다.

## 8. OCR 부분 실패

이미지 단위 OCR 오류는 문서 전체 실패와 구분합니다.

- 성공한 일반 텍스트와 OCR 결과를 유지합니다.
- 실패한 이미지만 제외합니다.
- 실패 건수와 오류 종류를 집계합니다.
- 원본 이미지와 OCR 원문을 로그에 남기지 않습니다.
- 검색 가능한 청크가 하나 이상이면 부분 성공할 수 있습니다.
- 검색 가능한 청크가 전혀 없으면 인제스트 전체를 실패 처리합니다.

## 9. synthesis 부분 실패

답변 단계의 문서별 실패는 색인 보상과 별개입니다.

- 한 문서 검색 실패: 다른 문서로 계속
- 한 문서 부분 Claude 실패: 다른 부분 답변으로 계속
- 한 문서 근거 부족: 해당 문서만 제외
- 유효 문서가 없음: Claude 호출 없이 `insufficient_evidence`
- 범위·인용 무결성 위반: 전체 요청 실패

부분 성공 답변은 실패 문서의 빈 출처나 오류 정보를 `sources`에 추가하지 않습니다.

## 10. ingest-complete 콜백

### 성공 콜백

- 최신 활성 문서와 전체 청크 스냅샷을 단일 진실 공급원으로 사용합니다.
- Chunk ID, 순번, 원문, Hash, 토큰 수와 출처 메타데이터를 전달합니다.
- 임베딩 벡터, Presigned URL, 토큰과 DB 정보를 전달하지 않습니다.

### 처리 실패 콜백

- `success=false`와 공개 가능한 제한된 오류 메시지만 전달합니다.
- `index_version`, `chunk_count`, `chunks`는 전달하지 않습니다.
- 실패 콜백 자체가 실패해도 최초 처리 오류를 유지합니다.

### manifest 조회 실패

manifest 조회 자체가 실패하면 같은 Backend 호출이 다시 실패할 가능성이 높으므로
추가 실패 콜백을 보내지 않고 원래 오류를 호출자에게 전달합니다.

### 성공 콜백 시작 후 오류

성공 콜백 전송이 시작된 뒤 네트워크 오류가 발생하면 실패 콜백을 연이어 보내지 않습니다.
Backend가 성공 요청을 반영했는지 알 수 없는 상태에서 `FAILED`로 덮어쓰는 일을 방지합니다.

## 11. 운영 확인 항목

재인제스트 실패 시 다음 순서로 확인합니다.

1. `RAG_Index_Run` 최신 상태와 오류 종류
2. `RAG_Document`의 활성·soft delete 상태
3. Qdrant point의 `users_idx`, `file_idx`, `rag_document_idx`, `is_active`
4. 동일 `File_IDX`의 최신 SUCCESS 실행
5. Backend 파일 상태와 ingest-complete 수신 결과
6. 보상 실패 이벤트 로그
7. 임시 다운로드 파일과 추출 이미지 정리 여부

## 12. 테스트 기준

다음 시나리오는 실제 E2E 또는 통합 테스트로 유지합니다.

- 동일 파일 중복 요청의 멱등 수렴
- 같은 `File_IDX` 동시 인제스트
- 파서·Embedding Model·Index Version 변경 재색인
- Qdrant 업서트 부분 실패
- 활성 전환 실패와 이전 point 복구
- Local 성공 확정 실패
- 실행 소유권 상실
- OCR 이미지 일부 실패
- 성공 콜백 최신 스냅샷
- 실패 콜백의 청크 미포함
- 성공 콜백 오류 뒤 실패 콜백 미전송
